# Taste
- 使用中文交流，期望以中文得到回复与解释。Confidence: 0.7
- 设计或实现功能前，期望先对照权威来源与参考实现（协议规范及其源码、zed、waku 的对应实现），而不是凭假设推断；尤其涉及 UI 形态时应引用参考实现的具体做法与出处，并诚实说明哪些没查、哪些没验证。也会对已给出的结论追问「真的是这样吗」（包括代码注释/模块文档里转述的说法），要求回到源码或 vendored schema 逐项核实，并在发现原判断不准确时明确更正。Confidence: 0.8
- 会以结构化形式（严重级别如 P1/P2 + 文件:行号 + 根因描述）提交问题清单，并要求先「核实」再修复：逐条对照源码确认是否属实、说明实际根因（若比报告更严重就点明），修完还要给出验证结果与仍然存在的边界/未验证项，而不是只报完成。定级要务实：明确区分「今天已经坏掉」与「只是潜在风险」，给出触发链并说明为何尚未触发，而不是按代码异味硬套级别。Confidence: 0.65
- 面向中文用户的 UI 文案用中文，代码、注释与标识符保持英文（界面语言与代码语言刻意分离）。Confidence: 0.6
- 改动后以可执行的验证收尾为准：`cargo fmt`/`check`/`clippy`/`test` 全绿，并做一次启动烟测确认不 panic，不留残留进程。Confidence: 0.6
- UI 走精简路线：菜单/列表项倾向于纯文字、文案从简，不要加装饰性图标（明确要求「删除会话不要加 icon」、「删除会话 改为 删除」）。Confidence: 0.5
- 选择器/列表项只显示名称等必要信息即可，不要在行里展示来源提供的冗长说明（明确要求 mode 只显示 `build`/`plan`，不要 agent 的描述文本）；宁可把这类数据从来源处直接去掉，也不在渲染时丢弃。触发用的 chip 同理只显示取值本身，不加类别前缀（明确要求去掉 sandbox chip 上的「沙箱」二字，只留「只读/工作区写入/完全访问」，与既有 model/mode chip 风格一致）。Confidence: 0.55
- 代码评审期望覆盖全部 diff，并从「代码架构、代码复用、组件化、代码质量」等多个维度给出分析，而非只挑功能缺陷。Confidence: 0.5
- 提出「分析某个模块的实现架构」时，期望得到分层的深度解读：模块边界与解耦方式、线程/并发与所有权模型、通道与数据流、状态归属、关键设计决策及其权衡与已知约束，并附具体「文件:行号」引用，而不是泛泛的概念概述。Confidence: 0.5
- UI 布局偏好：需要用户即时决策/操作的控件（如权限审批卡）放在输入区（composer）上方、始终可见，而不是内联在会滚动的对话流中；宁可牺牲「挂在那次具体调用上」的关联性，也要保证决策入口不移位。Confidence: 0.5
- 反对把「调用方必须记得手动做」的不变式留在各个调用点：倾向抽共享挂载点（如 `src/ui/layers.rs::window_layers`）让所有窗口统一走它，理由是这类失败模式静默无害化（弹窗没渲染和压根没弹看起来一模一样），并接受为此多抽一层抽象。Confidence: 0.6
- 判断某个 workaround 能否删除时，要求跨版本比对上游源码（如 gpui-component 0.6.0 vs 0.6.1 的 `Root::render`）确认行为是否已变，而不是假设「等升级就能删」。Confidence: 0.6
- 解释框架/库坑的知识应集中放进共享 helper 的 doc comment，调用点只留一行；注释必须解释「为什么」，否则读者会误判其用途（如把 `.relative()` 当成 dialog 定位所需）。Confidence: 0.6
- 反对 API 倒置与冗余参数：调用方能从现有上下文派生的东西（如 `cx.weak_entity()` 之于传入的 `WeakEntity`）不应作为参数要求调用方再传一次，签名也要与同类既有方法（如 `delete_session(…, cx: &mut Context<Self>)`）保持一致。Confidence: 0.55
- 明确反对把一次性要求上升为通则：指出把「删除会话不要 icon」概括成「菜单/列表项一律不要装饰性图标」会在带图标的工具栏等场景误导，宁可保留为窄范围、低置信度的记录。Confidence: 0.6
- 单文件明显过大（如 1000+ 行）时要求做模块化拆分：拆成同级模块目录（`src/x.rs` → `src/x/mod.rs` 门面 + 若干职责单一的子文件），而不是继续在单文件里堆叠。Confidence: 0.6
- 结构性重构要求是「纯搬迁」：公共 API、运行行为、并发/通道模型不变，外部调用点零改动，且不在同一 diff 里夹带顺带的内部整理（不抽内联闭包、不合并重复逻辑）；判定标准用「外部文件零改动」这类可核对的条件，而不是凭估算。Confidence: 0.55
- 拆分模块时测试跟随被测模块分布（纯函数测试进对应子模块、只在同模块可访问的私有字段测试留在该子模块、共享测试工具单独成文件），而不是全部堆在 mod.rs 底部。Confidence: 0.45
- 遇到需要决策的边界（拆分力度、测试归属）宁可先问清再动手，而不是按自己的判断直接改完。Confidence: 0.45
- 分发/运行时上明确排斥引入 Node.js 依赖（「我不想让用户在引入一个 nodejs 的应用」）：宁可选纯原生二进制（Rust）方案、自己承担协议适配成本，也不让用户侧出现 Node 运行时（npx/Homebrew 带 node、内嵌 bun/JS 运行时都不接受）。Confidence: 0.6
- 协议/集成的实现途径上倾向「不依赖第三方 crate，对着官方文档自己写」：明确表示「用这个 crate，不如参考这个（官方文档）自己写」，对来源非官方、版本陈旧（停留在旧协议）的第三方封装不信任；宁可自研适配并承担 schema 漂移成本，也不引入不可靠的依赖。Confidence: 0.6
- 会话设置中真正正交的轴各自拥有独立的 composer chip，而不是被折叠进已有 chip：沙箱策略单独成一个 chip 与 model/mode chip 并列，而不当作 Codex 的「mode」上报——硬塞进 mode chip 会叫错名字，也会挤掉剩下的轴。Confidence: 0.7
- 倾向把外部权威规范（如 codex app-server 的 JSON schema）的快照 vendor 进仓库、并按版本 pin（新版本另开目录做 diff），而不是只留在临时目录或依赖本机安装：这样手写的协议类型能随时与权威定义对照，升级时也有可比对基线。Confidence: 0.45
- 客户端不得覆盖 agent 自身的配置，除非用户显式选择某个值：未设置即「继承」，不发送任何字段，选择器如实显示「跟随 Agent 配置」，而不是替用户编一个默认值来悄悄收紧/放宽其原有配置。Confidence: 0.85
- 工具栏（composer）控件按归属关系相邻排列：推理深度紧挨模型选择器之后（排在 mode、sandbox 之前），因为它是该模型的属性而不是 session 级设置——而不是按功能重要性或既有顺序摆放。Confidence: 0.45
- 允许并期望为 composer chip 加一个与概念语义相配的前置图标（推理深度配 brain 图标，与 model chip 前置 agent logo 对齐）；图标集里没有时倾向自己落一份（vendored 的 `assets/icons/brain.svg`）并用项目 asset 机制覆盖在图标库之上，而不是退而求其次用近似图标。Confidence: 0.4
- 期望后端的协议差异各自在 backend 内部归一化，边界上只暴露单一形状；UI 代码不得按「正在使用哪个后端/协议」分支（遵守 AGENTS.md 的「协议类型止步于 backend 边界」约束）。宁可让某一后端把自身的 per-model 数据在内部折算成统一字段再上报，也不让 UI 去分辨两种形状做 fallback。Confidence: 0.7
- 对 codex、claude code、opencode 这类常见且用户量大的 agent，允许并期望在 backend 内部做针对性的定制化实现，而不是为了与其它后端「整齐一致」而牺牲适配质量：唯一的硬约束是与 UI 层的接口保持统一（Event/Cmd 单一形状、UI 不得按后端分支）。后端之间可以各写各的、只对齐边界形状。Confidence: 0.8
- 提交工作区时倾向一次性提交：多次明确说「提交所有 diff」「全部提交」，期望把当前全部改动（含互不相关的多条改动线）放进同一个 commit，而不是拆成多个或逐块挑选。Confidence: 0.5
- UI 尺寸避免「凭空的固定值」：容器/行应按内容自适应（可配 min/max 夹取）而不是写死宽高，尤其不要为不存在的内容预留空间；发现 `w(px(280.))` 之类无依据的硬编码即视为浪费并倾向删除。Confidence: 0.5
- 分清「本次改动引入的问题」与「既有问题」：改动前就存在、且落在未触碰文件里的告警（如 clippy 的 12 条）不顺带修，而是逐条核对行号确认新增为 0 条并单独列为既有问题（「我没有去动这些越界修复」）。Confidence: 0.5
- 未经许可不要在用户真实环境里做「有副作用」的验证：跑真实 agent 轮次（消耗额度）或在 `~/.codex` 等目录留下 rollout/历史记录，都要先说明代价并征求同意，而不是擅自跑完再解释。Confidence: 0.55
- 查看用户本机数据（sqlite 状态库、会话日志等）时先把快照复制到 scratchpad 再查询，绝不在用户正在使用的库上做操作；也用这类真实数据的分布/计数来做实证，而不是只停在规范文本的推断上。Confidence: 0.5
- 不呈现当前状态下无法生效的控件：功能被规则关掉时应整块隐藏（如会话锁定后不再渲染 agent 选择轨道），而不是留在原地置灰或「点了没反应」的静默空操作；决策守卫留在逻辑层兜底，UI 层只提供真正可用的动作。Confidence: 0.5
- 面对列出的多个缺陷倾向「全部修掉」而不是只挑最相关/最省事的一个先修：以一句「修掉」回应「要我把 P2-1、P2-2、P3-4 都修掉吗，还是先只修 P2-1」，期望可修的缺陷一次性处理完，只把需要拍板的接口语义变更（拒绝 vs 报错这类）留下再问。Confidence: 0.5
- 修复缺陷时把「与兄弟实现保持一致」当作默认做法：先核实同级实现（如同为选择器的 pick_mode/pick_sandbox/pick_reasoning）的既有写法，让偏离的那个对齐它们，改动范围与措辞也与之一致，而不是为特例新造一套逻辑；补的回归测试也顺带断言幂等性（如重复 init 后索引仍只有一个）。Confidence: 0.45
- 发起异步操作（如发送消息）后要立刻出现可见的加载/进行中状态，不接受从触发到首个后端事件之间「没有任何反应」的静止窗口（用户以「发起信息后没有任何反应，应该有一个类似 load 的状态显示」提出）；加载态是静态图标还是动画也在意，倾向于真正会动、能读出「正在加载」的实现。Confidence: 0.5
- 汇报进度时用平实语言说明每项待办「到底是什么、为什么值得做」，不要只用内部编号/简写（如只用 P2-3、P3-3 指代）就抛出「要不要顺手做」的开放式追问，否则用户会先回问「什么意思，你要做什么」；不确定是否该继续时，先明确说清「已完成、现在什么都没做」再问，而不是把可选收尾项与未完成的修复混在一起。Confidence: 0.35
